Integración de Sistemas

Análisis y diseño para integración

Fuentes de datos y límites de sistemas

  • En una integración real es muy importante identificar qué sistemas participan, qué tipo de datos manejan y quién es responsable de cada entidad de negocio (cliente, pedido, factura, etc.).

Fuentes de datos y límites de sistemas

  • Esto implica listar sistemas origen (por ejemplo, e‑commerce, ERP, facturación, inventarios) y determinar para cada uno qué operaciones ofrece (consultar, crear, actualizar) y qué tan “oficiales” son sus datos.

Fuentes de datos y límites de sistemas

  • A partir de esta identificación se definen los puntos de integración: qué APIs REST se deben exponer, qué servicios existentes se reutilizarán (incluyendo posibles servicios SOAP) y qué datos deben sincronizarse o solo consultarse bajo demanda.

Fuentes de datos y límites de sistemas

  • Tener claros estos límites evita que varias APIs modifiquen el mismo dato de forma descoordinada, lo que generaría inconsistencias difíciles de resolver.

Latencia y granularidad de servicios

  • La latencia aceptable entre sistemas condiciona cuán “finas” o “gruesas” deben ser las operaciones expuestas.

Latencia y granularidad de servicios

  • Si un flujo requiere respuestas casi en tiempo real (por ejemplo, validación de pago en línea), conviene exponer servicios relativamente compactos y evitar secuencias largas de llamadas síncronas entre muchos sistemas, ya que cada salto añade retraso.

Latencia y granularidad de servicios

  • Cuando la latencia tolerable es mayor (por ejemplo, integración nocturna de reportes), se puede optar por llamadas más pesadas o incluso por mecanismos por lotes.

Latencia y granularidad de servicios

  • En el diseño de APIs REST, esta reflexión se traduce en decidir si un cliente hace muchas llamadas pequeñas o menos llamadas más ricas, equilibrando simplicidad, rendimiento y claridad.

Requisitos de seguridad en la integración

  • Desde el análisis se deben capturar requerimientos de confidencialidad (qué datos deben viajar siempre cifrados), integridad (qué mensajes necesitan firma o verificación) y trazabilidad (qué operaciones deben dejar rastro detallado).

Requisitos de seguridad en la integración

  • Para cada flujo de integración se puede describir quién llama a quién, qué identidad usa y qué información mínima se necesita para autorizar la operación, sin entrar aún en protocolos concretos.

Requisitos de seguridad en la integración

  • Esto sirve de base para más adelante elegir mecanismos específicos de autenticación y autorización en las APIs REST o, donde corresponda, perfiles de seguridad en servicios SOAP existentes.
